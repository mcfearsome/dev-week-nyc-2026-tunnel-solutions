rendezvous · the first tnls plugin

Send a big file through a door that evaporates. // peer-to-peer over BitTorrent — scoped to one file, dead on a TTL, and the relay never sees a byte.

Dropbox and ngrok move a file by copying it onto someone else's server. rendezvous keeps the bytes peer-to-peer and uses a capability tunnel only to authorize which file a teammate may pull — and for how long. Then the link dies.

the wedge
Moving bytes isn't new. Moving them peer-to-peer while scoping them at the capability level is.

The relay only ever brokers permission — it pairs two sockets by id and shuttles opaque frames. The file itself never passes through it, so you don't pay for the bandwidth and no third party holds your data. The same tunnel that says yes, this file, for thirty minutes also hands the downloader the seeder's address — so the transfer connects the instant the link is opened.

The relay carries permission, not payload. It introduces the peers and forwards the magnet; the bytes go straight between machines. A compromised relay can't read your file, widen the scope, or extend the TTL — it only moves opaque frames.

the rendezvous trick

plain BitTorrent
⌛

discovery by DHT

The getter has only a magnet, so it asks the DHT and public trackers to find the seeder. On one host, the same LAN, or behind hairpin NAT, that often never connects in a useful window.

$ tnls get … waiting for peers… (DHT)
with rendezvous
⚡

introduction by tunnel

share gathers its reachable addresses — loopback, every LAN IP, and its public IP from the relay's /whoami — and ships them through the tunnel. get feeds them straight to BitTorrent as initial_peers.

$ tnls get … peer 127.0.0.1 connected · 0s

Same transfer mechanism either way — rendezvous just skips the search. Unreachable hints fail silently; the DHT and trackers remain as the fallback.

the plugin model
rendezvous is a plugin. It can only ever narrow.
declares

its scope

A file share needs exactly two tools: request_file and list_shares. That's the entire capability the link exposes.

constrained

only narrows

It selects an allowlist of tool names — it can't widen a TTL, forge a token, or reach the relay. Adding a capability adds no trust.

isolated

never sees the secret

The host stays the sole agent; the plugin is spawned over stdio exactly like any MCP server. The 32-byte signing key never leaves the host.

The host/plugin split is landing step by step. Today this ships as tnls share / tnls get; under the plugin model the commands become tnls rendezvous share / tnls rendezvous get — same behavior, same single enforcement point.

honest limits
When the direct path works — and when it falls back.
✓
loopback & same-LAN

Always connects directly — the advertised 127.0.0.1 and LAN addresses are reachable, so the transfer starts immediately.

~
public internet

Connects when UPnP maps the seeder's port and your router preserves it — the common consumer case. The public address comes from the relay's /whoami, no third-party echo service.

→
hard / symmetric NAT

No direct hole-punch yet; it falls back to the DHT and trackers. The relay never becomes a data fallback — it carries permission, never payload. (True hole-punching is future work.)

get started
# install the CLI
$ cargo install tnls

# share a file on a scoped link that expires
# (bytes stay peer-to-peer; default relay is tunnel.locker)
$ tnls share ./big.mov --ttl 30m
# → prints https://tunnel.locker/t/<id>#<token>

# on the other side — pull it straight from you
$ tnls get <link> --out ./tnls-downloads
Peer-to-peer,
but governed.

One file, one scope, one TTL. The bytes never leave your control plane's authority — close the tunnel and the link is dead, mid-transfer included.

tnls share seeds for the life of the process; Ctrl-C or the TTL tears it down and stops seeding.
